## Предметная область: интернет-магазин

```
customers 1 ──< orders 1 ──< order_items >── 1 products
```

| Таблица       | Что хранит        | Связи                                     |
| ------------- | ----------------- | ----------------------------------------- |
| `customers`   | покупатели        |                                           |
| `products`    | товары            |                                           |
| `orders`      | заказы            | `customer_id` → `customers.id`            |
| `order_items` | позиции в заказе  | `order_id` → `orders.id`, `product_id` → `products.id` |

## Запуск

```bash
# 1. Собрать тегированный образ приложения
docker build -t rzps-app:1.0 ./app

# 2. Запустить БД и adminer
docker compose up -d db adminer

# 3. Запустить приложение в интерактивном режиме (в той же сети, что и БД)
docker compose run --rm app
```

Логин: `app_user`, пароль: `AppPassword123`.

SQL-скрипты из папки `sql` выполняются автоматически **только при первом запуске**, пока БД пустая.
Чтобы пересоздать БД с нуля: `docker compose down -v`, затем снова шаг 2.

Логи дублируются в файл `logs/app.log` (на компьютере, рядом с compose.yaml).

## Пункты меню ↔ пункты задания

| Меню | Пункт задания | Что делает                                                  |
| ---- | ------------- | ----------------------------------------------------------- |
| 1    | 6.1           | `SELECT * FROM table`                                       |
| 2    | 6.1           | `SELECT ... WHERE колонка = значение`                        |
| 3    | 6.1           | `SELECT ... WHERE кол1 = знач1 AND кол2 = знач2`             |
| 4    | 6.2           | `UPDATE ... SET кол1 = ..., кол2 = ... WHERE id = ...`       |
| 5    | 6.2           | `UPDATE ... SET кол = ... WHERE кол IN (знач1, знач2, ...)`  |
| 6    | 6.3           | `INSERT` одной строки                                       |
| 7    | 6.3           | заказ в `orders` + товар в `order_items` (id через `RETURNING`) |
| 8    | 6.4           | несколько строк в одну таблицу                              |
| 9    | 6.4           | несколько заказов, в каждом несколько товаров               |

Примеры для демонстрации:
- меню 2 → `products` → `category` → `Электроника`
- меню 3 → `orders` → `2,4` → customer_id `1`, status `оплачен`
- меню 5 → `orders` → `status` → `отменён` → по `id` → `4,5`
- меню 7 → покупатель `1`, товар `3`, количество `2`, цена `5000`
- ошибка: меню 7 → покупатель `999` → «Ссылка на несуществующую запись»

## Как это работает (на вопросы преподавателя)

**Защита от SQL-инъекций.**
- Значения передаются только через плейсхолдеры `%s` — psycopg отправляет их в БД отдельно от текста запроса, поэтому они никогда не становятся частью SQL-кода.
- Названия таблиц и колонок нельзя передать через `%s`. Поэтому пользователь выбирает их **по номеру из списка** `TABLES` (белый список), а в запрос они вставляются через `sql.Identifier(...)`, который оборачивает имя в кавычки.
- Для `IN (...)` на каждое значение создаётся свой плейсхолдер: `IN (%s, %s, %s)`.

**Транзакции.** Каждый пункт меню — одна транзакция: при успехе `commit()`, при ошибке `rollback()`.
Если в меню 7/9 заказ создался, а товар указан неверно — заказ тоже отменяется.
(id из последовательности при этом «сгорает», поэтому в нумерации могут быть пропуски — это нормально.)

**Логи.**
- Успех → `stdout` (`[OK] ...`), ошибка → `stderr` (`[ОШИБКА] ...`), пользователю показывается понятный текст.
- Если задана переменная окружения `LOG_FILE`, те же записи дублируются в файл, а для ошибок — вместе с настоящим текстом ошибки от БД.

**Права `app_user`.** Только `SELECT`, `INSERT`, `UPDATE` на таблицы и `USAGE` на последовательности (для `SERIAL`).
Удалять строки и менять структуру таблиц не может.
(После 4 задания права разделены — см. ниже.)

# 4 ЗАДАНИЕ — исправления по итогам моделирования угроз

Пять мер из выводов отчёта (папка `4`) внесены в код. Старый код не удалён, а закомментирован
с пометкой `ИЗМЕНЕНО ПО ЛАБОРАТОРНОЙ РАБОТЕ 4 В СООТВЕТСТВИИ С ПРОБЛЕМОЙ N`,
новый код помечен `ДОБАВЛЕНО ПО ЛАБОРАТОРНОЙ РАБОТЕ 4 ...`.

| Проблема | Что сделано | Где |
| -------- | ----------- | --- |
| 1. Пароли в репозитории | Пароли вынесены в Docker secrets — файлы `secrets/*.txt` (папка в `.gitignore`), старые пароли сменены | `compose.yaml`, `sql/03_user.sql`, `.gitignore` |
| 2. Порты открыты в сеть | Порты публикуются только на `127.0.0.1`; Adminer — только через HTTPS-прокси | `compose.yaml` |
| 3. Подбор пароля | Новые 24-символьные пароли; в приложении 3 попытки входа с паузой; в СУБД `auth_delay` (пауза 2 с после ошибки) и `CONNECTION LIMIT 5` | `app/app.py`, `compose.yaml`, `sql/03_user.sql` |
| 4. Избыточные права | `app_user` — оператор: меняет только контакты покупателя, статус заказа и количество; новый `app_manager` — менеджер с полными правами; аудит всех изменений в таблице `audit_log` | `sql/03_user.sql`, `sql/04_audit.sql` |
| 5. Нет шифрования и бэкапов | TLS в PostgreSQL (сертификат создаётся при сборке), приложение подключается только по TLS; HTTPS для Adminer (Caddy); резервная копия `pg_dump` раз в сутки в `./backups` | `db/Dockerfile`, `compose.yaml`, `app/app.py`, `db/backup.sh` |

## Запуск после изменений

```bash
# 0. Пароли: папка secrets/ с тремя файлами (в каждом только пароль, без пустой строки в конце)
#    secrets/db_admin_password.txt, secrets/app_user_password.txt, secrets/app_manager_password.txt

# 1. Пересоздать БД — иначе останутся старые пароли и права (скрипты из sql/ выполняются только на пустой БД)
docker compose down -v

# 2. Собрать образ приложения и запустить всё, кроме приложения
docker build -t rzps-app:1.0 ./app
docker compose up -d --build db adminer adminer-https backup

# 3. Приложение
docker compose run --rm app
```

Порты 5432 и 8080 не должны быть заняты другими проектами (например, `demotask`) — остановите их перед запуском.

| Учётная запись | Пароль | Роль |
| -------------- | ------ | ---- |
| `app_user` | `secrets/app_user_password.txt` | Оператор: смотрит всё, добавляет заказы, меняет контакты/статус/количество |
| `app_manager` | `secrets/app_manager_password.txt` | Менеджер: может менять всё, включая цены |
| `postgres_admin` | `secrets/db_admin_password.txt` | Администратор СУБД (в Adminer, сервер `db`) |

- Adminer: **https://localhost:8443** (браузер предупредит о самоподписанном сертификате — принять).
- Журнал аудита (под `postgres_admin`): `SELECT * FROM audit_log ORDER BY id;`
- Резервные копии: папка `backups/`, восстановление:
  `pg_restore -h localhost -U postgres_admin -d testdb --clean backups/<файл>.dump`

**Проверка для демонстрации:** войти как `app_user` → меню 4 → `products` → изменить `price` →
«Недостаточно прав для этой операции». Под `app_manager` то же самое проходит, а в `audit_log`
видно, кто и что изменил.
